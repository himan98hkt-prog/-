# 피아노학원 자동 반주(MR) 엔진 — 1~5단계

피아노 악보(MusicXML·MIDI)를 넣으면 **곡의 화성을 자동 분석해** 오케스트라 반주를
만들어 주는 엔진. 개발지시서 9장의 **1단계(엔진)** 구현분이다.

전 과정이 로컬 연산이다. **API 호출 0회.**

```bash
python3 mr.py score.mxl --style chamber --level normal --bpm 84 -o out.mp3
```

## MR 이 무엇인지부터

**출력에는 원곡 피아노가 들어가지 않는다. 반주만 나온다.** 피아노는 아이가 친다.
원곡이 음원에 섞여 있으면 아이는 자기 연주와 녹음된 피아노를 겹쳐 치게 되고,
그건 MR 이 아니라 감상용 데모다.

```bash
python3 mr.py score.mxl -o out.mp3                 # 반주만 (기본)
python3 mr.py score.mxl --mix full -o 확인용.mp3    # 피아노 + 반주 (확인·감상용)
python3 mr.py score.mxl --mix piano -o 원곡.mp3     # 피아노만
```

여기서 따라 나오는 것이 두 가지 있다.

**① 반주는 곡 전체에 깔린다.** 지시서 5장은 `build`(곡을 4등분해
off → simple → normal → rich)를 기본으로 제안했지만, 그건 음원에 피아노가 있다고
보았을 때의 이야기다. 반주만 내보내면서 그 곡선을 쓰면 **곡의 앞 1/4 이 완전한
무음**이 되어 아이가 그동안 맞출 것이 없다. 그래서 기본은 `flat`(전체에 깔림)이고,
`build` 는 발표회용으로 남겨 뒀다 — 무대에서는 아이 혼자 시작했다가 오케스트라가
밀려드는 그 효과가 실제로 살아난다.

```bash
python3 mr.py score.mxl --curve build -o 발표회.mp3
```

**② 시작 신호가 필요하다.** 피아노가 없으니 아이는 반주가 어디서 시작하는지 알 수
없다. 혼자 연습할 음원이면 카운트인을 구워 넣는다.

```bash
python3 mr.py score.mxl --count-in 1 -o 연습용.mp3
```

카탈로그 곡은 카운트인 1마디가 기본이다.

## 설치

```bash
pip install -r requirements.txt
apt-get install fluidsynth ffmpeg fluid-soundfont-gm   # SoundFont 포함
```

SoundFont 경로는 `/usr/share/sounds/sf2/FluidR3_GM.sf2` 를 기본으로 찾는다.
다른 것을 쓰려면 `MR_SOUNDFONT` 환경변수로 지정한다.

## 쓰는 법

```bash
# 화성만 확인 (음원 안 만듦) — 화성 확인 화면이 보여 줄 내용
python3 mr.py score.mxl --analyze-only

# 연습용 mp3 하나
python3 mr.py score.mxl --style march --level normal --bpm 84 -o out.mp3

# 연습용 192k + 무대용 320k + 영상편집용 WAV + 파트별 스템
python3 mr.py score.mxl --all-formats --stems --out-dir out

# 카운트인 4마디 + 조옮김
python3 mr.py score.mxl --count-in 4 --transpose -2 -o out.mp3

# 반주 MIDI 를 남긴다 (카탈로그에 저장할 것은 오디오가 아니라 이 파일)
python3 mr.py score.mxl --keep-midi --out-dir out

# 편성 스타일 7종
python3 mr.py --styles
```

`--analyze-only` 출력:

```
조성: C major   박자: 4/4   마디: 12   세그먼트: 18

m1   C    │ m2   G7   C    │ m3   F    C    │ m4   G7   C
m5   F    │ m6   C    │ m7   G7   │ m8   C

확인 필요 2곳 (2위 후보와 점수 차가 작음 — 화성 확인 화면에서 노란색이 될 구간):
   m7-1  G7   (다음 후보: Bdim / G)
   m9-1  F    (다음 후보: Dm / Bdim)
```

마지막 블록이 지시서 10장의 **노란색 강조** 대상이다. 엔진이 세그먼트마다
`conf`(1위와 2위의 점수 차)와 `alts`(다음 후보 3개)를 같이 내보내므로,
2단계 확인 화면은 이 값만 읽어서 색칠하면 된다.

## 2단계 — 카탈로그와 화성 확인 화면

```bash
python3 seed_catalog.py          # 씨앗 곡 넣기 (아래 참조)
python3 serve.py                 # http://127.0.0.1:8765  화성 확인 화면
python3 catalog_cli.py status    # 제작 현황

# 미리 만들어 두기 — 반주 MIDI + 편성 변형 + MR mp3
python3 catalog_cli.py build --all --styles strings,chamber,march --audio
```

### 화성 확인 화면 (지시서 10장)

> "PDF 경로가 실용적이냐 아니냐가 이 화면 하나로 갈린다."
> "악보를 음표 단위로 교정하면 40분, 화성만 보면 3~5분"

그래서 이 화면은 **음표를 아예 보여주지 않는다.** API 도 음표를 내보내지 않는다
(`test_view_carries_no_notes_only_chords` 가 이를 지킨다).

| 지시서 10장 요구 | 구현 |
|---|---|
| 음표가 아니라 화음 이름만 | 마디 카드 + 화음 이름. 음표 데이터는 서버가 안 보낸다 |
| 각 칸은 드롭다운 | 조성의 화음이 먼저, 그 외 전체가 뒤에 |
| 바꾸면 즉시 반주 재생성 | 화음이 바뀌면 렌더 키가 바뀌어 자동 재생성 (약 2초) |
| 자신 없는 구간은 노란색 | 1위와 2위의 점수 차(`conf`)가 작은 칸. "다음 후보"도 같이 |
| 해당 마디만 구간 재생 | 마디마다 ▶ 버튼 |
| 조성 확인 UI 불필요 | 없다. 대신 자동 판정이 흔들리는 악보는 `--key` 로 못 박는다 |

확인 화면만은 **피아노 + 반주**로 들려준다. 화음이 이 곡에 맞는지는 선율이 같이
들려야 판단할 수 있기 때문이다. 원장님께 나가는 것은 반주만이고, 화면에서도
`듣기` 로 골라 들을 수 있다.

**검수 부담이 실제로 얼마나 줄어드는가** — 26곡 764칸 중 노란색은 **78칸(10%)** 이다.
96마디짜리 클라라 슈만 폴로네즈도 확인할 칸이 128개 중 6개다. 나머지는 훑고 넘어간다.

구간 재생은 서버를 다시 부르지 않는다. 받아 둔 mp3 안에서
`초 = 마디 시작(4분음표) × 60 / bpm` 으로 건너뛴다. 템포가 일정해서 이 환산이 정확하다
(브라우저 실측: ♩=126 곡의 3번 마디 → 3.81초, 오차 0.0초).

화면은 곡별 **검수 시간을 자동으로 기록한다.** 지시서의 "곡당 20분 이내" 목표가
지켜지는지 `catalog_cli.py status` 에서 바로 보인다.

### 카탈로그

```bash
python3 catalog_cli.py import score.mxl --title "체르니 100번 5번" --id czerny100_05 \
    --composer "Carl Czerny" --book "체르니 100" --level 3 --public-domain --style march
python3 catalog_cli.py list --status analyzed
python3 catalog_cli.py show czerny100_05      # 화성 격자를 터미널에서
python3 catalog_cli.py build --all            # 반주 MIDI 미리 굽기
python3 catalog_cli.py export player.json     # 3단계 플레이어용 번들
```

### 미리 만들어 두기

```bash
python3 catalog_cli.py build --all --styles strings,chamber,march --audio
```

씨앗 26곡 기준 실측 — **반주 MIDI 26개 + 편성 변형 78개 = 180.7 KB, 97초.**
같은 것을 오디오로 저장했다면 약 406 MB 다.

템포별로는 굽지 않는다. MIDI 는 재생할 때 템포를 바꾸면 되기 때문이다(지시서 8.4).
바뀌는 것은 **편성(스타일·두께)** 뿐이라 그것만 변형으로 남긴다.
`--audio` 를 붙이면 MR mp3 까지 캐시에 구워 둬서 현장에서 기다리지 않는다.

디스크 배치 — **오디오는 카탈로그가 아니다** (지시서 6장):

```
catalog/
  catalog.json          곡 메타 + 확정된 화성 + 검수 상태   ← 백업 대상
  scores/<id>.musicxml  원본 악보                          ← 백업 대상
  midi/<id>.mid         반주 MIDI (1 KB 미만)              ← 백업 대상
  cache/<key>.mp3       렌더 캐시 — 지워도 2초면 다시 생긴다
```

저작권(지시서 7장)은 **파일을 복사하기 전에** 검사한다. 블랙리스트에 걸리거나
`--public-domain` 이 없으면 악보가 디스크에 남지 않는다.

### 카탈로그에 무엇이 들어 있나

`seed_catalog.py` 가 **이 환경에서 합법적으로 확보 가능한 곡만** 넣는다 — 26곡:

- 퍼블릭도메인 피아노곡 6곡 (music21 코퍼스): 바흐 평균율 1권 1번 전주곡,
  모차르트 K.545 1악장 제시부, 클라라 슈만 폴로네즈 Op.1 네 곡 (64~96마디)
- 자사 오리지널 연습곡 20곡 (회귀 테스트 세트와 같은 곡)

지시서 2단계의 목표는 **약 150곡** (체르니 100 전곡 + 바이엘 후반 + 부르크뮐러 25)이다.
그 악보들은 MuseScore.com·IMSLP 에서 **사람이 골라 받아야 하고, 여기서는 못 했다.**
받아 오면 `catalog_cli.py import` 로 같은 자리에 들어가고 파이프라인은 그대로 돈다.

## 발표회 운영 화면 (프로그램 대시보드)

```bash
python3 serve.py            # http://127.0.0.1:8765/static/program.html
```

지시서 모듈 ⑤-3 의 큐 리스트와 ⑤-2 의 페이드아웃. 카탈로그의 MR 을 실제로 튼다.

- 순서대로 세팅, 곡이 끝나면 **다음 곡 자동 대기** (자동 재생은 하지 않는다 — 무대는 원장님이 연다)
- **반주 페이드아웃** 버튼 — 실측 **3.04초** (지시서 11장 기준: 3초 내 완전 무음)
- 다음 곡을 미리 받아 둬서 무대에서 기다리지 않는다
- 스페이스=재생/정지, Esc=페이드아웃, ←→=순서 이동

무대 장면(커튼·조명·먼지·피아노)은 **CSS 와 인라인 SVG** 다. 이미지 파일이 없어도,
네트워크가 죽어도 화면이 뜬다 — ⑤-1 이 "연주홀 와이파이는 믿을 수 없다"고 한 이유다.
`server/static/img/` 에 `hall.mp4`/`hall.jpg` 를 넣으면 그 위에 얹힌다.

자세한 것은 [docs/MR-DASHBOARD.md](../docs/MR-DASHBOARD.md).

## 3단계 — 플레이어 PWA

```bash
python3 serve.py
# 태블릿 브라우저에서 http://<PC주소>:8765/static/player/ → "홈 화면에 추가"
```

지시서 모듈 ⑤. *"반주 파일은 콘텐츠고, 팔리는 건 현장에서 안 터지는 운영 도구다."*

- **오프라인 재생** — ⤓ 를 한 번 누르면 전곡을 받아 둔다. **서버가 죽어도 돈다**
- 템포·조옮김·구간 루프·마디 점프 — 다시 받지 않고 그 자리에서 바뀐다
- 페이드아웃 3초 · 카운트인 · 곡별 볼륨 · 아이별 설정
- **집 연습 링크** — 설정을 URL 에 실어 보낸다. 받는 쪽은 설치도 로그인도 없다
- 발표회 큐를 열면 `1. 김지우 — 작은 왈츠 (C장조) · ♩=84 · 동화풍 · 보통`

mp3 가 아니라 **반주 MIDI 를 받아 브라우저에서 합성한다.** 같은 곡 실측으로
mp3 499,437 B 대 MIDI 609 B — 820배다. 26곡을 통째로 오프라인에 넣어도 **121 KB**.
템포를 바꿔도 다시 받을 것이 없다.

> **카운트인만 이어폰으로 듣기(⑤-4)** 는 `AudioContext.setSinkId` 를 쓴다.
> 크로미움 110+ 에만 있고 **iOS 사파리에는 없다.** 없는 브라우저에서는 그렇다고
> 화면이 말한다. 아이패드를 쓸 계획이면 이 기능만 크롬이 필요하다.

브라우저에서 실제로 돌려 보는 검사가 있다 (CI 도 매번 돌린다):

```bash
pip install playwright && python3 -m playwright install chromium
make player
```

자세한 것은 [docs/MR-PLAYER.md](../docs/MR-PLAYER.md).

## 4단계 — PDF 악보 올리기

```bash
python3 serve.py
#   PDF 올리기   http://127.0.0.1:8765/static/upload.html
```

원장님이 PDF 악보를 올리면 → 악보 인식(OMR) → **화성 확인 화면** → 반주.

**"올리면 바로 완성"이라고 말하지 않는다.** 지시서 2.2 의 실측대로 OMR 은 90~95%
라서 32마디에 2~6마디가 틀린다. 그래서 인식이 끝난 작업은 「완료」가 아니라
**「화성 확인 대기」** 로 가고, 확인 전에 완료로 넘기려 하면 거절한다.

**월 업로드 제한의 단위는 쪽이다.** 지시서 8.2 의 과금 단위가 스캔(=쪽)이기
때문이다 — 작업 수로 세면 40쪽짜리 한 편에 한 달 예산이 날아간다.

```bash
python3 catalog_cli.py limit 6      # 월 6쪽 (쪽당 400원 → 최대 월 2,400원)
python3 catalog_cli.py uploads      # 올라온 악보와 이번 달 몫
python3 catalog_cli.py sweep        # 오래 들고 있던 PDF 삭제 (지시서 7장)
```

**올린 PDF 를 서버가 들고 있지 않는다** (지시서 7장 "서버 영구 저장·재배포 금지").
PDF 는 `catalog/incoming/` 에만 잠깐 있다가 MusicXML 이 오는 순간 지워진다.
실패해도, 취소해도, 프로세스가 죽었다 살아나도 지워진다. CI 가 매번 확인한다.

> **OMR 공급사 API 는 실제로 못 돌려 봤다.** 이 작업을 한 컨테이너에서 `klang.io` 와
> `api-docs.klang.io` 가 조직 egress 정책에 막혀 문서를 볼 수 없었다. 주소를
> 지어내 하드코딩하는 대신 **전부 설정으로 뺐다** — 키가 생기면 환경변수만 채우면
> 되고 코드는 안 고친다. 기본값은 **신청제**(사람이 1~2일 안에 납품)라서 키가
> 없어도 4단계 전체가 오늘 돌아가고, 지시서 8.3 ③ 이 권하는 방식이기도 하다.

자세한 것은 [docs/MR-UPLOAD.md](../docs/MR-UPLOAD.md).

## 5단계 — 관리노트 연동

**학생 명단을 두 번 치지 않는다.** 관리노트에서 명단을 내보내고 반주가 받는다.

```
관리노트 → 설정 → 백업·복원·내보내기 → 「피아노 반주(MR) 연동」
반주    → python3 catalog_cli.py roster 명단.json
```

넘어가는 것은 **id·이름·반·재원여부** 넷뿐이다. 연락처·메모·수납 할인은 반주를
만드는 데 하나도 안 쓰이고, 넘기면 개인정보가 두 시스템에 흩어진다. 10명 명단 실측
834바이트, 연락처 0건.

**이름이 아니라 학생 id 로 연결한다.** 관리노트에서 개명하면 발표회 화면도 따라
바뀐다. 명단에 없는 학생은 저장해 둔 이름을 그대로 쓴다 — 발표회 당일 화면이 비면
안 되기 때문이다.

**인증키는 관리노트와 같은 것 한 장이다.** 통합키(`A`)와 피아노키(`K`)가 열고
학원 전용키(`M`)는 안 연다.

```bash
export MR_LICENSE_KEY=ALAB-CDEF-XYEV
```

키를 보는 곳은 **PDF 업로드 하나뿐이다.** 돈이 나가는 유일한 경로라서다(지시서 8.1).
카탈로그 제작·발표회 운영·**집 연습 링크**는 묻지 않는다 — 지시서 ⑤-10 이
「설치·로그인 없이 재생」이라고 못 박았고, 학부모에게 인증키를 물을 수는 없다.

> 인증키 규칙은 `src/core/license.js` 가 원본이고 `piano_mr/license.py` 는 이식본이다.
> 한 글자만 달라도 **이미 판 키가 죽는다.** 그래서 CI 가 node 를 실제로 돌려 양쪽 답을
> 대조하고, **건너뛰면 실패**시킨다.

자세한 것은 [docs/MR-LINK.md](../docs/MR-LINK.md).

## 원장님께 드리는 것 — 배포 꾸러미

원장님 PC 에 파이썬·fluidsynth·SoundFont 를 깔게 할 수는 없다. 그럴 필요도 없다 —
플레이어가 런타임에 부르는 건 **곡 목록과 반주 MIDI 둘뿐**이고 둘 다 그냥 파일이다
(지시서 8.4). 그래서 앱이 부르는 **그 경로 그대로** 깔아 두면 정적 호스트에서 돈다.

```bash
python3 catalog_cli.py package ../dist/반주 --academy "행복피아노"
#   곡 26개 · 파일 39개 · 전체 172 KB (반주 45 KB)
```

| | 누가 쓰나 | 고객에게 나가나 |
|---|---|---|
| 카탈로그 제작 서버 (`serve.py`) — 화성 확인·PDF 업로드 | 우리 | ✗ |
| **플레이어 꾸러미** (정적 파일) | 원장님 | ✅ |

**악보 원본과 렌더 캐시는 꾸러미에 안 들어간다.** 용량 때문만이 아니라, 넣으면
악보를 재배포하는 모양이 되기 때문이다 (지시서 7장). 테스트가 막는다.

주소는 전부 상대경로라 `/반주/` 같은 **하위 폴더에 올려도 그대로 돈다.**
HTTPS 여야 오프라인과 홈 화면 설치가 켜진다.

```bash
python3 tools/player_check.py --static /tmp/pkg
```

`--static` 은 MR 서버가 아니라 **평범한 정적 서버**로 띄워 11항목을 본다. 그 뒤
서버를 죽이고 오프라인 재생까지 확인한다 — "원장님 PC 에 파이썬이 필요 없다"의
유일한 증거다. CI 가 매번 돌린다.

배포 절차 전체는 [docs/DEPLOY.md](../docs/DEPLOY.md) 5장.

## 회귀 테스트

```bash
python3 bench.py                # 곡별 표
python3 bench.py --stages       # 프로토타입 -> 현재까지 무엇이 얼마나 올렸나
python3 -m pytest               # 정확도 게이트 포함 404개
```

```
곡                             화성    7화음까지   조성     틀린마디      시간
---------------------------------------------------------------
p01_block_c               100.0%   100.0%   O     0/8     0.03s
...
p17_two_four_pickup        82.4%    58.8%   X     2/9     0.03s
---------------------------------------------------------------
전체                         99.5%    95.7%   95%   2/165   0.05s
```

**정답지를 사람이 받아 적는 대신 정답에서 악보를 만든다.** `fixtures/pieces.py` 에
화음 진행을 적으면 `build_fixtures.py` 가 그 진행대로 울리는 악보를 만든다.
그래서 정답지에 오류가 섞일 수 없다. 20곡 전부 **자사 오리지널**이라
저작권 문제도 없다 (지시서 7장 화이트리스트의 마지막 항목).

측정 단위는 세그먼트가 아니라 **시간**이다. 엔진이 마디를 어떻게 쪼개든
"곡의 몇 %를 맞는 화음으로 반주했는가"가 실제로 들리는 품질이기 때문이다.

곡 20개가 덮는 것: 장조 6개·단조 5개 조성, 4/4·3/4·2/4·6/8·3/8 박자,
블록화음·알베르티·왈츠·분산화음·브로큰옥타브·2성부 짜임새,
마디당 1~4개의 화성 변화, 못갖춘마디, 반복기호, 자리바꿈, 부속화음, 딸림7화음.

## 무엇을 고쳤나 (1단계 보강)

지시서 9장이 "현 프로토타입의 검증 범위 밖"이라고 지목한 **3박자·단조·화성이 잦은 곡**.
점수 계산식의 상수(miss 0.9 / 베이스 0.30·0.10 / 연속성 0.06)는 **하나도 건드리지
않았다.** 고친 것은 전부 "세그먼트를 어디서 자를지"와 "후보에 무엇을 넣을지"다.

| # | 고친 것 | 왜 |
|---|---|---|
| 1 | 박(beat)에 맞춘 분할 | 3/4 마디가 1.5박씩 잘려 박을 가로질렀다. 이제 3/4 는 1 또는 3조각, 6/8 은 1 또는 2조각. 4/4→2조각(K.545 검증 동작)은 그대로 |
| 2 | 적응형 분할 | 마디마다 조각 수를 스스로 고른다. `설명력 − 0.10×(조각수−1)` 이 최대인 쪽 |
| 3 | 못갖춘마디 | `barDuration` 대신 실제 길이로 창을 잡는다. 안 그러면 분석 창이 옆 마디로 넘어간다 |
| 4 | 단조의 vii° | 화성단음계 이끔음 감삼화음을 후보에 추가 |
| 5 | V/vi 누락 | 지시서 5장은 V/V·V/vi·V/IV 를 쓰라는데 프로토타입에 V/vi 가 빠져 있었다 |
| 6 | 딸림7화음 | G 와 G7 을 구분한다. 단, **3음과 b7 이 둘 다 울릴 때만** |
| 7 | 멜로디 최저음 | `parts[0]` 대신 매 시점의 최고음을 쓴다. 그랜드스태프가 한 파트로 들어온 악보에서 왼손 저음까지 멜로디로 세던 문제 |
| 8 | 이음줄 | 이어진 음의 뒷부분에는 첫 박 가중 ×1.5 를 주지 않는다 |

무엇이 얼마나 올렸나 (20곡 전체 · `python3 bench.py --stages`):

| 구성 | 화성 정확도 | 7화음까지 | 틀린 마디 |
|---|---|---|---|
| 프로토타입 방식 (마디 분할 + 3화음만) | 85.3% | 66.2% | 50 / 165 |
| + 딸림7화음 · V/vi 후보 | 87.1% | 82.9% | 46 / 165 |
| + 박에 맞춘 고정 분할 | 93.9% | 89.9% | 19 / 165 |
| **+ 적응형 분할 (현재)** | **99.5%** | **95.7%** | **2 / 165** |

되돌렸을 때 정확도가 안 떨어지는 '보강'은 군더더기다. 이 순서를 그대로
`tests/test_regression.py::test_every_stage_of_the_fix_earned_its_place` 가 지킨다.

## 알려진 한계

**플레이어 음색은 서버 렌더와 다르다.** 브라우저는 SoundFont 를 못 쓰므로 Web Audio
감산합성으로 낸다. 연습·리허설·발표회 진행에는 이쪽이 맞다 (즉시 반응·오프라인·템포
자유). 하지만 **발표회 영상에 붙일 음원은 서버에서 mp3 로 구울 것** — 그쪽이
FluidR3_GM 을 쓴다.

**카운트인만 이어폰으로 빼는 기능은 브라우저를 탄다.** `AudioContext.setSinkId` 가
크로미움 110+ 에만 있다. iOS 사파리에는 없다.

**OMR 공급사 API 는 실제로 돌려 본 적이 없다.** 이 작업을 한 컨테이너에서
`klang.io`·`api-docs.klang.io` 가 조직 egress 정책에 막혀 문서를 볼 수 없었다.
주소·헤더·필드 이름을 전부 설정으로 빼 뒀으니 키가 생기면 환경변수만 채우면 된다.
멀티파트·폴링·실패 처리는 진짜 HTTP 서버를 띄워 확인했지만, **공급사 필드 이름이
맞는지는 한 번 돌려 봐야 안다.** 기본값은 신청제라 키 없이도 돌아간다.

**조성 판정이 짧고 성긴 악보에서 흔들린다.** 20곡 중 1곡(`p17`, 8마디 2/4,
왼손이 근음 옥타브뿐)에서 music21 이 C장조를 F장조로 읽었다. 지시서 2.2 의
"조성은 40% 틀려도 100% 정확"은 K.545 처럼 충분한 길이의 곡에서 측정한 값이고,
16박짜리 악보는 그 통계가 설 자리가 없다. 조성만 정해 주면(`--key C`) 같은 곡이
82.4% → 88.2% 로 올라가고, 20곡 전체는 99.5% → 99.7% 가 된다.

→ **지시서 10장의 "조성 확인 UI는 불필요" 판단은 카탈로그 곡(대부분 16마디 이상)에는
그대로 유효하다.** 다만 곡 레코드에 조성을 확정해 두고 엔진에 넘기는 편이 안전해서
`--key` 와 `score_loader.load(key_name=...)` 를 열어 뒀다.

남은 오차 1마디(`p17` m4)는 F 베이스 위에 B♮ 가 지나가는 자리로, 엔진이 읽은
`G7/F` 가 정답지의 `F` 보다 오히려 타당하다. 정답지 쪽 한계로 보고 두었다.

**연습 기록을 관리노트로 되돌리기.** 한 번 만들었다가 되돌렸다.

연동은 **관리노트 → 반주** 한 방향이다. 명단이 넘어오고, 반주는 그것으로 발표회 순서를
짠다. 연습 기록은 그 반대 방향을 새로 여는 것이고, 그 순간 반주 프로그램이 학원 관리
데이터를 만들어 내는 쪽이 된다.

이 프로그램이 파는 것은 **악보를 넣으면 반주가 나오는 것**과 **발표회 당일 안 터지는
운영 도구**다. 아이가 며칠 연습했는지를 모아 학부모에게 보고하는 건 학원 관리의 일이고,
그건 관리노트가 한다. 자세한 경위는 [docs/MR-LINK.md](../docs/MR-LINK.md) 5장.

## 설계상 손대면 안 되는 것

지시서 12장. 실패를 거쳐 나온 값과 구조다.

1. **세그먼트 단위 분석** — 마디 단위(1화성/마디)로 하면 K.545 를 놓친다
2. **베이스(최저음) 가중** — 정확도를 크게 올린다. 상성부 가중은 오히려 해롭다
3. **패드를 멜로디 최저음 아래로** — 안 그러면 아이의 선율이 묻힌다
4. **`chordify().root()` 금지** — F장조를 A장조로 오판한 전력이 있다
5. **점수식 상수** — `tests/test_harmony.py::test_scoring_constants_unchanged` 가 지킨다
