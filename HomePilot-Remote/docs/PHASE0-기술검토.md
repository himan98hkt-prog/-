## 2. 원격제어 기술 비교

| 방식 | 장점 | 단점 | 상용 판매 적합성 |
|---|---|---|---|
| **RustDesk 재사용/포크** | 완성도 높음, P2P+중계, H.264/VP9 | 클라이언트·서버 모두 **AGPL-3.0** → 앱 전체 소스 공개 의무. 상표 사용 불가. 거대한 코드베이스 유지보수 부담 | ❌ 폐쇄형 유료 앱에는 부적합 (소스 공개형으로 팔 경우만 가능) |
| **Windows RDP** | OS 내장, 화질 좋음 | **Windows Home 은 RDP 호스트 불가**, 외부 접속 시 포트 개방/VPN 필요(공격 대상), 휴대폰 앱은 MS 클라이언트 의존 | ❌ 일반 소비자 제품 기반으로 부적합 |
| **WebRTC** (libwebrtc BSD, flutter_webrtc MIT) | NAT 통과(ICE/STUN/TURN), 하드웨어 코덱, 낮은 지연 | 구현 복잡, TURN 서버 비용, Windows 쪽 네이티브 통합 작업 큼 | ✅ 라이선스 문제 없음 → **Phase 3 이후 직접 연결용으로 채택 예정** |
| **자체 구현 (채택)**: Rust 에이전트 + WebSocket 중계 + Noise 종단간 암호화 | 코드 전부 소유(폐쇄형 판매 가능), 단순·감사 가능, 모바일 데이터/CGNAT 에서도 항상 동작 | 처음엔 중계만 사용(서버 대역폭 비용), 영상 효율은 단계적 개선 필요 | ✅ |

### 채택한 구조 (요약 — 자세한 내용은 `ARCHITECTURE.md`)
```
[Android 앱] --wss--> [중계 서버] <--wss-- [Windows 에이전트]
      \___________ Noise XX 종단간 암호화 ___________/
```
- PC 와 휴대폰이 모두 **바깥으로** 중계 서버에 접속 → 공유기 포트 개방 불필요, 휴대폰 모바일 데이터(통신사 CGNAT)에서도 동작.
- 중계 서버는 **암호문만 전달**: 화면·키 입력·인증 비밀을 볼 수 없고 저장하지 않음.
- Phase 3 에서 같은 Wi-Fi 직접 연결, UDP 홀펀칭(WebRTC/ICE) 직접 연결을 추가하고, 실패 시 중계로 자동 전환.

## 3. 핵심 기능 구현 가능성 (실제 확인 결과)

| 기능 | 방식 | 확인 수준 |
|---|---|---|
| 화면 캡처 | GDI `BitBlt` (+ 커서 합성). 모든 Win10/11 호환 | Windows 대상 **컴파일 성공**, 실제 Windows 실행은 CI(Windows 러너)·사용자 PC 에서 확인 필요 |
| 영상 인코딩 | 프레임별 JPEG (축소·품질·FPS 조절, 변화 없으면 전송 생략, ack 기반 흐름 제어) | Linux 테스트 화면으로 **동작 확인** (디버그 빌드 약 9 fps / 목표 10 fps) |
| 원격 입력 | `SendInput` — 마우스 절대좌표(다중 모니터 가상 데스크톱), 휠, **유니코드 입력으로 한글 직접 전달**, 특수키/조합키 | 변환 로직 단위 테스트 + 종단간 테스트 통과. 실제 입력 반영은 Windows 실기 확인 필요 |
| 다중 모니터 | `EnumDisplayMonitors`, 모니터별 선택 | 테스트 모드 2개 모니터로 확인 |
| CPU/RAM/디스크 | sysinfo | 동작 확인 |
| GPU 사용률 | Windows 성능 카운터 `GPU Engine(*engtype_3D)` | 컴파일 성공, 실기 미검증. 측정 불가 시 0% 가 아니라 "측정 불가"로 표시 |

### 할 수 없는 것 (정직한 한계)
- **UAC 확인창·잠금 화면·Ctrl+Alt+Del 화면**: Windows 보안 데스크톱이라 일반 프로그램은 캡처/입력할 수 없습니다. 우회하지 않습니다. (상용 제품들은 서명된 Windows 서비스 + 사용자 세션 에이전트 구조로 해결 → Phase 8 검토 항목. UAC 를 끄거나 우회하는 방식은 쓰지 않음)
- **관리자 권한으로 실행된 창**에는 일반 권한 에이전트가 입력할 수 없습니다(UIPI). 에이전트를 관리자 권한으로 실행하면 가능하지만 기본값으로 하지 않습니다.
- **Ctrl+Alt+Del** 은 `SendInput` 으로 보낼 수 없습니다(OS 설계).
- JPEG 방식은 고해상도·고FPS 에서 대역폭이 큽니다(1080p 50% 축소 기준 수 Mbps). H.264 하드웨어 인코딩(Media Foundation)은 후속 성능 과제입니다.

## 4. 네트워크 (사설망 · 공유기 NAT · 모바일 데이터)

| 환경 | 직접 연결 | 중계 연결 (현재 구현) |
|---|---|---|
| 같은 Wi-Fi | 가능 (Phase 3: 로컬 탐색) | 가능 |
| 외부 Wi-Fi ↔ 집 공유기 | 대부분 UDP 홀펀칭 가능 (Phase 3) | 가능 |
| 모바일 데이터 (국내 통신사 CGNAT) | 대칭형 NAT 이면 실패 잦음 | **가능** (바깥 방향 TCP 443 만 필요) |
| 회사/학교 방화벽 | 대부분 차단 | wss(443) 이면 대부분 가능 |

→ **중계 연결을 기본 보장 경로로** 먼저 만들고, 직접 연결은 최적화로 추가하는 순서가 안전합니다.

### 중계 서버를 어디에 둘 것인가 (비용 발생 → 사용자 승인 필요)
| 선택지 | 비용 | 비고 |
|---|---|---|
| A. 집 PC 에서 중계 실행 + **Cloudflare Tunnel** 로 외부 공개 | 무료 | 포트 개방 불필요, wss 자동. `cloudflared` 설치 필요 (설치 전 승인 받음) |
| B. 집 PC 에서 중계 실행 + 공유기 포트포워딩 + 인증서 | 무료 | 공유기 설정·인증서 관리 필요, 포트 노출 |
| C. 클라우드 소형 VPS (월 약 5~7천원 수준) | 유료 | 상용화 시 필수. **승인 전에는 만들지 않음** |

현재는 **아무 서버도 만들지 않았고 비용도 발생하지 않았습니다.** 개인용 MVP 는 A 를 추천합니다.

## 5. 라이선스 · 재배포 검토

### 사용한 라이브러리 (Windows 빌드 그래프 실측, 2026-10-13)
`cargo metadata` 로 실제 포함되는 외부 패키지 약 200개를 확인했습니다.
- MIT / Apache-2.0 / BSD / ISC / Unicode / Zlib 계열: 대부분 — 폐쇄형 상용 배포 가능 (고지문 포함 필요)
- **GPL / AGPL / LGPL: 없음**
- 주의 1: `option-ext` (MPL-2.0, `dirs` 의 하위 의존성) — 파일 단위 약한 카피레프트. 수정하지 않고 쓰면 상용 배포 가능, 고지 필요.
- 주의 2: `jpeg-encoder` 는 IJG 라이선스 포함 — 문서에 "this software is based in part on the work of the Independent JPEG Group" 고지 필요.
- 배포 전 `cargo-about` 또는 `cargo-deny` 로 고지문(THIRD-PARTY-NOTICES) 자동 생성 예정 (Phase 7).

### 기타 상용화 위험
| 항목 | 위험 | 대응 |
|---|---|---|
| RustDesk 코드 | AGPL 전염 | **사용하지 않음** (아이디어만 참고, 코드 복사 금지) |
| H.264 특허 | 코덱 로열티 | OS 내장 인코더/디코더(Windows Media Foundation, Android MediaCodec) 사용 시 일반적으로 OS 측 라이선스로 처리. 자체 코덱 배포 금지 |
