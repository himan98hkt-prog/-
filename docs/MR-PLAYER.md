# 피아노 자동 반주 — 3단계 작업 보고 (플레이어 PWA)

개발지시서 **모듈 ⑤** 구현 결과. 지시서가 이 모듈에 달아 둔 말은
「**여기가 실제 상품**」이고, 그 근거도 같이 적혀 있다 —
*"반주 파일은 콘텐츠고, 팔리는 건 현장에서 안 터지는 운영 도구다."*

코드는 [`mr/server/static/player/`](../mr/server/static/player), 1·2단계 보고는
[MR-ENGINE.md](MR-ENGINE.md) · [MR-CATALOG.md](MR-CATALOG.md).

```bash
cd mr
python3 seed_catalog.py --catalog catalog     # 곡 넣기 (한 번)
python3 serve.py --catalog catalog            # 띄우기
# 태블릿 브라우저에서 http://<PC주소>:8765/static/player/ → "홈 화면에 추가"
```

## 2. 오프라인을 어떻게 진짜로 만들었나

지시서 ⑤-1 은 *"학원·연주홀 와이파이는 믿을 수 없다"* 를 이유로 든다. 그러면
**서버가 아예 죽은 상태에서 되는지**를 봐야 한다.

### mp3 를 캐시하지 않고 MIDI 를 캐시한다

같은 곡(16초, 작은 왈츠) 실측:

| | 크기 | 26곡 전체 |
|---|---|---|
| 렌더한 mp3 | 499,437 B | 수 MB |
| 반주 MIDI | **609 B** | **45.2 KB** |

820배 차이다. 게다가 mp3 는 **템포마다 한 벌씩** 필요하다 — ♩=84 로 구운 파일로는
♩=92 연습을 못 한다. MIDI 를 받아 브라우저에서 합성하면 그 문제가 통째로 사라진다
(지시서 ⑤-5 *"MIDI 기반이라 실시간 변경 가능. 사전 렌더 불필요"*).

오프라인 한 벌의 실측 총량:

```
앱 껍데기 (HTML·CSS·JS·아이콘)   61 KB
곡 목록 (26곡)                   14 KB
반주 MIDI 26곡                   45 KB
─────────────────────────────────────
합계                            121 KB
```

### 브라우저의 오프라인 흉내는 믿으면 안 된다

처음엔 Playwright 의 `set_offline(True)` 로 검사했는데, 이게 **페이지의 요청만 막고
서비스워커 안에서 부르는 `fetch` 는 그대로 내보낸다.** 그 상태로 통과한 검사는
"오프라인에서 된다"를 증명하지 못한다 — 워커가 몰래 서버에 다녀왔을 뿐이다.

실제로 재 봤더니 그랬다. 오프라인을 켠 채로:

```
/api/stats                → FAIL Failed to fetch      (페이지 요청 — 막힌다)
/api/player/midi/…        → ok 200                    (워커 안 요청 — 안 막힌다)
/api/player/midi/__없는곡__ → ok 404  ← 서버가 살아 있다는 증거
```

그래서 지금 검사는 **서버 프로세스를 `terminate()` 한 뒤** 본다. 덤으로 브라우저
HTTP 캐시도 CDP `Network.clearBrowserCache` 로 지운다. 남는 건 서비스워커 캐시뿐이다.

검사에 이빨이 있는지도 확인했다 — "오프라인 준비"를 누르지 않고 서버만 내리면
곡 목록이 뜨지 않고 검사가 실패한다.

### 목록도 워커 캐시에 넣는다

첫 방문 때는 서비스워커가 아직 페이지를 잡기 전이라 곡 목록 요청이 워커를 안 거치고
지나간다. 그러면 오프라인에서 목록이 뜨는 건 브라우저 HTTP 캐시 **운**이지 설계가
아니다. 지금은 "오프라인 준비"가 목록도 명시적으로 받아 워커 캐시에 넣는다.

### 미리 받는 주소와 재생하는 주소가 같아야 한다

이게 조용히 틀리기 제일 쉬운 자리였다. 재생할 때는 편성을 붙여서 부르는데
(`/api/player/midi/곡?style=chamber&level=normal`) 미리 받을 때는 편성 없이 받아
두면, 오프라인에서 정확히 맞는 캐시가 없다. 워커는 "대충 같은 곡"을 내주고,
**화면에는 「실내악」인데 스피커에서는 기본 편성이 나온다.**

두 군데를 손봤다.

- 주소를 만드는 함수(`midiUrl`)를 하나로 만들어 미리 받기와 재생이 같은 걸 쓴다.
- 그래도 없는 편성을 요청하면, 말없이 바꿔치기하지 않고 `X-MR-Fallback: default`
  헤더를 붙여 내보낸다. 화면은 「오프라인이라 기본 편성으로 재생합니다」를 띄운다.

검사 [6]·[9]·[10] 이 이 셋을 각각 지킨다.

## 3. 브라우저에서 반주를 만든다

`js/midi.js` 가 SMF 를 파싱하고, `js/synth.js` 가 Web Audio 로 합성하고,
`js/engine.js` 가 시간을 관리한다. 외부 라이브러리 0개, 빌드 단계 0개.

### 시간 축은 초가 아니라 박

```js
get positionBeat() {
  return this._anchorBeat + (this.ctx.currentTime - this._anchorTime) * this.bpm / 60;
}
```

음표 목록을 박 단위로 들고 있으면 템포 변경은 **환산식만 갈아 끼우는 일**이 된다.
`setTempo()` 는 지금 박 위치에 닻을 다시 내리고 bpm 만 바꾼다 — 재생 중에 끊김 없이
빨라지고 느려진다. 초 단위로 들고 있었다면 전체를 다시 계산해야 했다.

시계는 `setTimeout` 이 아니라 `AudioContext.currentTime` 을 쓴다. 25 ms 마다 깨어나
0.18초 앞까지 예약해 두는 look-ahead 방식이라, 브라우저가 잠깐 바빠도 박이 밀리지
않는다.

### 파서에서 한 번 크게 틀렸던 곳

```js
const trackLen = u32();
const end = p + trackLen;
```

처음엔 `const end = p + u32();` 라고 썼다. 자바스크립트는 왼쪽 `p` 를 **먼저** 읽고
나서 `u32()` 를 부르기 때문에, `u32()` 가 `p` 를 4 밀기 전의 값으로 끝 위치가 잡힌다.
모든 트랙이 4바이트씩 짧게 끝났다. 곡 끝의 음이 잘려 나가는데 앞부분은 멀쩡해서
눈으로는 잘 안 보인다 — 길이를 먼저 변수에 받는 것으로 고쳤다.

### 페이드아웃은 `linearRampToValueAtTime`

```js
fadeOut(seconds = FADE_SECONDS)
```

`setTargetAtTime` 은 지수 접근이라 **영원히 0 에 닿지 않는다.** 지시서 ⑤-2 는
"3초 안에 반주만 사라짐"이고, 발표회장에서 -60 dB 는 무음이 아니다. 선형 램프로
정확히 0 을 찍는다. 실측 3.02~3.05초 (검사 [5] 가 매번 잰다).

## 4. 카운트인을 원장님 이어폰으로만 (⑤-4)

지시서는 *"스피커로 / 이어폰으로 원장님만 듣기 선택"* 을 요구한다. 반주는 홀
스피커로 나가고 딸깍 소리만 원장님에게 가려면 **출력 장치를 둘로 갈라야 한다.**

`AudioContext.setSinkId` 로 카운트인 전용 컨텍스트를 만들어 다른 장치에 붙인다.
두 컨텍스트는 시계가 다르므로, 예약하는 그 순간의 차이를 재서 밀어 준다:

```js
at = startTime - this.ctx.currentTime + this.cueCtx.currentTime;
```

미리 저장해 둔 오프셋을 쓰면 틀어진다 — 예약 시점에 한 번 재는 것이 중요하다.
카운트인은 몇 초짜리라 두 시계의 드리프트는 문제가 되지 않는다.

양쪽을 동시에 재서 확인했다:

| | 이어폰 | 스피커 |
|---|---|---|
| 카운트인 2마디 동안 | **0.0056** | 0 |
| 반주가 시작된 뒤 | 0 | **0.3574** |

**`setSinkId` 는 크로미움 110+ 에만 있다. iOS 사파리에는 없다.** 없는 브라우저에서는
버튼을 눌러도 「이 브라우저는 소리를 두 곳으로 나눠 보내지 못합니다」라고 말한다 —
되는 척하지 않는다. 아이패드를 쓸 계획이라면 이 기능만 크롬이 필요하다.

## 5. 서버가 새로 내주는 것

| 주소 | 하는 일 |
|---|---|
| `GET /api/player/bundle` | 곡 목록 + 발표회 프로그램. **오디오 주소는 들어가지 않는다** |
| `GET /api/player/midi/{id}?style=&level=` | 반주 MIDI. 없으면 그 자리에서 굽는다 |

번들에 `.mp3` 가 섞이면 오프라인 설계가 통째로 무너지므로, 테스트가 그걸 막는다
(`test_player_bundle_carries_no_audio`). MR 에 원곡 피아노가 섞이지 않는 것도
채널 검사로 못 박았다 (`test_player_midi_has_no_original_piano`) — 피아노는 채널 0,
반주는 1·2·3·4·5·9 다.

반주 MIDI 는 `max-age=31536000` 으로 영구 캐시한다. 화음을 고치면 곡을 다시 굽고
주소가 바뀌므로 오래된 걸 붙들 일이 없다.

## 6. 곁다리로 고친 것

**조성이 `E- major` 로 보였다.** music21 표기가 원장님 화면까지 그대로 나가고 있었다.
학원에서 쓰는 말은 「E♭장조」다. `catalog.key_label()` 을 만들어 플레이어·곡 목록·
화성 확인 화면 세 군데를 모두 고쳤다.

## 7. 아직 안 된 것

| 항목 | 상태 |
|---|---|
| 아이패드 사파리에서 카운트인만 이어폰으로 | **안 됨** — `setSinkId` 미지원 (위 4장) |
| 음색 | FluidR3_GM 이 아니라 Web Audio 감산합성이다. 현장 확인용으로는 충분하지만 **녹음용은 서버 렌더(mp3)를 쓸 것** |
| 4단계 PDF 업로드 · 5단계 관리노트 연동 | 미착수 (지시서 순서상 다음) |

음색에 대해 한 가지. 플레이어는 브라우저 합성이라 서버가 굽는 mp3 와 소리가 다르다.
연습·리허설·발표회 진행에는 이쪽이 맞다 (즉시 반응, 오프라인, 템포 자유). 하지만
**발표회 영상에 붙일 음원은 서버에서 mp3 로 구워야 한다** — 그쪽이 SoundFont 를 쓴다.
