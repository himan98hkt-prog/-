# 인증키(시디키) 운영 안내

판매자용 문서입니다. 고객에게 배포하지 마세요.

## 1. 키 형식

12자리, 표기는 4자씩 끊어 `APBC-DEFG-1234`.

| 자리 | 뜻 | 값 |
|---|---|---|
| 1 | 제품 | `A` 통합(피아노 관리노트 + 학원 관리노트) · `M` 학원 전용 · `K` 피아노 전용 |
| 2 | 플랜 | `L` Lite(단일 기기·오프라인) · `P` Pro(다기기·실시간 동기화) |
| 3~8 | 랜덤 | Crockford base32 (사람이 헷갈리는 I·L·O·U 제외) |
| 9~12 | 체크섬 | 제품 salt + 본문을 해시한 값 — 한 글자만 틀려도 거부 |

초기 발급분(첫 자리가 `L`/`P` 인 12자리)도 계속 인정합니다. 굳이 회수하지 않아도 됩니다.

## 2. 두 제품에서 같은 키를 쓰려면

1. 이 저장소의 `src/core/license.js` 를 **피아노 관리노트에 그대로 복사**합니다.
2. 피아노 쪽에서 `PRODUCT_CODE` 만 `'K'` 로 바꿉니다. (이 제품은 `'M'`)
3. 발급기에서 제품을 **통합(A)** 으로 골라 키를 발급하면 양쪽에서 열립니다.

`A` 키는 두 제품 모두 통과, `M` 키는 학원 관리노트에서만, `K` 키는 피아노 관리노트에서만 통과합니다.
잘못 넣으면 앱이 "○○ 전용 키입니다" 라고 이유를 표시합니다.

> 두 제품의 salt 가 같아야 합니다. `LICENSE_SALT` 는 두 앱에서 동일한 문자열이어야 하고,
> **출시 후에는 절대 바꾸지 않습니다.** 바꾸면 이미 판매한 키가 전부 무효가 됩니다.

## 3. 발급 절차

1. `npm run build` 후 `dist/tools/keygen.html` 을 로컬에서 엽니다. (고객 서버에 올리지 마세요)
2. 제품(보통 통합 A) · 플랜 · 수량 · 메모(주문번호)를 넣고 **키 발급**.
3. **CSV 저장** 으로 `key,product,plan,issued_at,memo` 를 보관합니다. 이 파일이 판매 대장입니다.
4. 고객에게는 키 문자열만 전달합니다.

## 4. 고객 화면에서 일어나는 일

- 첫 실행 → 인증 화면. 키 입력 또는 **14일 체험 시작**.
- 인증하면 IndexedDB 설정에 `{키, 키 해시, 플랜, 제품, 기기번호, 인증일}` 이 저장됩니다.
- 체험이 끝나면 다시 인증 화면이 뜨지만 **데이터는 그대로** 남아 있어 키를 넣으면 이어서 씁니다.
- 설정 > 인증키 · 플랜에서 키 교체, 이 기기 인증 해제가 가능합니다.

## 5. 문의 대응

| 상황 | 대응 |
|---|---|
| "키를 잃어버렸어요" | 판매 CSV 에서 주문번호·메모로 조회해 재전달 |
| "기기를 바꿨어요" | 같은 키를 새 기기에 입력하면 됩니다(오프라인 검증이라 횟수 제한 없음). 필요하면 기존 기기에서 인증 해제 요청 |
| "키가 안 들어가요" | 화면의 오류 문구를 물어보세요. `검증번호가 맞지 않습니다` = 오타, `○○ 전용 키` = 제품 불일치, `12자리입니다` = 자릿수 |
| "몇 번 기기인지 알고 싶어요" | 인증 화면·설정 화면 하단의 6자리 기기번호 |

## 6. 알려진 한계 (정직하게)

- 오프라인 자체검증이라 **키 공유를 기술적으로 막지 못합니다.** 브라우저 앱 특성상 salt 가 클라이언트에 포함되므로,
  작정하고 분석하면 키를 만들어 낼 수 있습니다. 이 방식은 "정품 구매 흐름을 만드는 것" 까지가 목적입니다.
- 강한 통제가 필요하면 Pro(Supabase) 쪽에 서버 검증을 붙이는 것이 정공법입니다.
  `academy_members` 테이블에 키 해시를 저장하고 학원 생성 시 서버에서 검증하는 방식으로 확장할 수 있습니다.
- 백업 파일에는 인증키가 들어가지 않으므로, 백업을 통한 라이선스 복제는 막혀 있습니다.
