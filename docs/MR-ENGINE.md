# 피아노 자동 반주(MR) 엔진 — 1단계 작업 보고

개발지시서(`피아노학원 자동 반주(MR) 프로그램 — 개발지시서`) 9장의 **1단계(엔진)**
구현 결과. 코드는 `mr/`, 사용법은 `mr/README.md`.

## 1. 완료 기준 대조

| 지시서 11장 항목 | 기준 | 실측 |
|---|---|---|
| 화성 정확도 | 회귀 테스트에서 95% 이상 | **99.5%** (20곡) |
| 생성 속도 | 1곡 5초 이내 | **1.8~2.3초** |
| API 호출 | 0회 | **0회** |

| 지시서 9장 1단계 체크리스트 | 상태 |
|---|---|
| 4개 모듈 이식·리팩터링 | 완료 |
| 회귀 테스트 세트 (20곡 정답 화성) | 완료 |
| 취약 케이스 보강 (3박자·단조·화성이 잦은 곡) | 완료 |
| CLI | 완료 |

2단계(카탈로그) 이후는 착수하지 않았다. 지시서 9장이 "순서를 바꾸지 말 것"이라고
명시했다.

## 2. 무엇을 고쳤고 각각 얼마나 올렸나

점수 계산식의 상수(miss 0.9 / 베이스 0.30·0.10 / 연속성 0.06 / 첫 박 ×1.5)는
**하나도 건드리지 않았다.** 지시서 12장이 "실패를 거쳐 나온 값"이라고 했고,
`tests/test_harmony.py::test_scoring_constants_unchanged` 가 이를 못 박는다.

고친 것은 전부 **세그먼트를 어디서 자를지**와 **후보에 무엇을 넣을지**다.

| 구성 | 화성 정확도 | 7화음까지 | 틀린 마디 |
|---|---|---|---|
| 프로토타입 방식 (마디 분할 + 3화음만) | 85.3% | 66.2% | 50 / 165 |
| + 딸림7화음 · V/vi 후보 | 87.1% | 82.9% | 46 / 165 |
| + 박에 맞춘 고정 분할 | 93.9% | 89.9% | 19 / 165 |
| **+ 적응형 분할 (현재)** | **99.5%** | **95.7%** | **2 / 165** |

`python3 bench.py --stages` 로 재현된다.

### 2.1 박(beat)에 맞춘 분할 — 3박자 곡

프로토타입은 `nseg = round(마디길이 / 2박)` 으로 잘랐다. 3/4 마디(3.0)는
`round(1.5) = 2` 가 되어 **1.5박씩 잘렸고, 경계가 박을 가로질렀다.**
이제 분할 후보는 박 수의 약수만 쓴다.

| 박자 | 분할 후보 | 기본값 |
|---|---|---|
| 4/4 | 1, 2, 4 | 2 (K.545 검증 동작 그대로) |
| 3/4 | 1, 3 | 1 |
| 6/8 | 1, 2 | 2 (점4분음표 단위) |
| 2/4 | 1, 2 | 1 |
| 12/8 | 1, 2, 4 | 4 |

### 2.2 적응형 분할 — 화성이 잦은 곡

마디마다 조각 수를 스스로 고른다.

```
점수 = 설명력(purity) − 0.10 × (조각수 − 1)
```

조각을 늘리면 각 조각은 **언제나** 더 잘 맞는다. 대가를 물리지 않으면 알베르티
베이스나 왈츠 반주에서 베이스가 움직일 때마다 그 음을 근음으로 착각해 화성이
잘게 흔들린다. 반대로 대가가 크면 K.545 처럼 2박마다 바뀌는 곡을 뭉갠다.

0.10 은 20곡 회귀 세트로 고른 값이고, 0.10~0.12 구간 전체가 98.6% 이상이라
한두 곡 때문에 흔들리는 값이 아니다.

> 시행착오 기록: 처음에는 "성기게 합쳐 보고 → 잘게 쪼개 보고" 두 단계 휴리스틱으로
> 짰는데, 두 단계가 서로의 결과를 되돌리면서 2화성 마디를 1화성으로 뭉개는 사고가
> 났다(-7.6%p). 단일 점수식으로 바꾸고 나서야 안정됐다.

### 2.3 딸림7화음 — 단, 트라이톤이 있을 때만

지시서 10장의 확인 화면 예시에 `G7` 이 나오므로 7화음은 1급 후보다.
장3화음 후보마다 딸림7화음 짝을 붙이되, **3음과 b7 이 둘 다 울릴 때만** 인정한다.
딸림7화음의 정체는 그 둘 사이의 트라이톤이기 때문이다.

이 조건이 없으면 4음 화음이 3음 화음보다 항상 많은 음을 "설명"해서 유령 화음이
정답을 밀어낸다. 실측에서 Bb장조 마디가 B♮ 없이 `G7` 으로 읽혔다.

### 2.4 나머지

| 고친 것 | 증상 |
|---|---|
| 못갖춘마디 | `barDuration`(박자표상 길이)으로 창을 잡아 분석이 옆 마디로 넘어갔다 |
| 단조 vii° | 화성단음계 이끔음 감삼화음이 후보에 없었다 |
| V/vi 누락 | 지시서 5장은 V/V·V/vi·V/IV 를 쓰라는데 프로토타입에 V/vi 가 없었다 |
| 멜로디 최저음 | `parts[0]` 을 멜로디로 가정해서, 그랜드스태프가 한 파트로 들어온 악보에서 왼손 저음까지 멜로디로 셌다. 이제 매 시점의 최고음을 쓴다 |
| 이음줄 | 이어진 음의 뒷부분에 첫 박 가중 ×1.5 가 잘못 붙었다 |
| 반복기호 | 전개 후 마디 번호가 겹치므로 연주 순서 인덱스를 따로 둔다 |

### 2.5 넣었다가 뺀 것

세그먼트 **안쪽** 박 머리에도 가중을 주는 안을 시험했다. 20곡 전체에서
±0.3%p(165마디 중 1마디) 안쪽으로만 움직였고 가중치를 키우면 다시 나빠졌다.
노이즈 수준의 이득을 위해 검증된 가중식에 상수를 더 붙이지 않았다.

## 3. 회귀 테스트 세트

**정답지를 사람이 받아 적는 대신, 정답에서 악보를 만들었다.**
`mr/fixtures/pieces.py` 에 화음 진행을 적으면 `build_fixtures.py` 가 그 진행대로
울리는 MusicXML 을 만든다. 정답지에 오류가 섞일 수 없고, 20곡 전부
**자사 오리지널**이라 저작권 문제도 없다(지시서 7장 화이트리스트의 마지막 항목).

곡 20개가 덮는 것:

- 조성: 장조 6개(C·G·F·D·Bb 등), 단조 5개(a·e·d·g·b)
- 박자: 4/4, 3/4, 2/4, 6/8, 3/8
- 짜임새: 블록화음, 알베르티, 왈츠, 분산화음, 브로큰옥타브, 2성부
- 화성 변화: 마디당 1개 ~ 박마다
- 그 외: 못갖춘마디, 반복기호, 자리바꿈, 부속화음, 딸림7화음

측정 단위는 세그먼트가 아니라 **시간**이다. 엔진이 마디를 어떻게 쪼개든
"곡의 몇 %를 맞는 화음으로 반주했는가"가 실제로 들리는 품질이기 때문이다.
지시서 2.2 표의 "32마디 중 틀린 마디"도 같이 센다.

## 4. 지시서 수치와 다르게 나온 것

### 조성 판정은 100% 가 아니었다

지시서 2.2 는 "조성 판정은 음표를 40% 틀려도 100% 정확했다 → 조성 확인 UI는
불필요"라고 한다. 20곡 중 **19곡에서는 그대로 맞았다.** 틀린 1곡은 `p17`
(8마디, 2/4, 왼손이 근음 옥타브뿐)로, music21 이 C장조를 F장조로 읽었다.

지시서의 측정은 K.545 처럼 충분한 길이의 곡에서 나온 값이고, 16박짜리 악보는
그 통계가 설 자리가 없다. **카탈로그 곡은 대부분 16마디 이상이므로 "조성 확인 UI
불필요" 판단 자체는 유효하다.** 다만 안전판으로 조성을 직접 넘길 수 있게 열어 뒀다
(`--key C`, `score_loader.load(key_name=...)`). 곡 레코드에 조성을 확정해 두고
넘기면 20곡 전체가 99.5% → 99.7% 가 된다.

### 나머지는 지시서 값과 맞았다

| 항목 | 지시서 | 실측 |
|---|---|---|
| MusicXML → 완성 mp3 | 2.2초 | 1.8~2.3초 |
| 반주 MIDI 크기 | 2.4 KB | 0.7 KB |
| API 호출 | 0회 | 0회 |
| 조성 판정 | 100% | 95% (20곡 중 19곡) |

## 5. 다음 단계가 바로 쓸 수 있는 것

2단계(카탈로그 · 화성 확인 화면):

- `harmony.analyze_segments()` 가 세그먼트마다 `conf`(1위와 2위의 점수 차)와
  `alts`(다음 후보 3개)를 낸다 → 지시서 10장의 **노란색 강조**를 그대로 그릴 수 있다
- `harmony.parse_label()` 가 사람이 타이핑한 화음 이름을 되읽는다 (이명동음 포함)
- `catalog.apply_corrections()` 가 교정을 반영하고 `harmony_verified` 를 세운다
- `mr.py --use-harmony h.json` 으로 **재분석 없이** 교정된 화성만으로 반주를 다시 만든다
- `catalog.check_copyright()` 가 블랙리스트와 `public_domain` 을 강제한다 (7장)

3단계(플레이어 PWA):

- `--count-in N` 이 카운트인 클릭을 앞에 붙인다 (모듈 ⑤-4)
- `catalog.Program.cue_lines()` 가 발표회 큐 목록 문자열을 만든다 (모듈 ⑤-3)
- 반주 MIDI 를 클라이언트에 내려주면 브라우저에서 템포·조옮김을 실시간으로 바꿀 수
  있다 (8.4). 스템과 음질 일관성이 필요한 경우를 위해 서버 렌더도 `render.py` 에 있다

## 6. 뒤늦게 바로잡은 것 — MR 은 반주만이다

1단계를 만들 때 출력이 **피아노 + 반주**였다. 이름이 MR 인데 원곡이 들어 있었으니
틀린 것이다. 아이가 피아노를 치면서 트는 음원에 녹음된 피아노가 섞여 있으면,
아이는 자기 연주와 녹음을 겹쳐 치게 된다. 그건 MR 이 아니라 감상용 데모다.

`--mix` 를 두고 기본값을 `mr`(반주만)로 바꿨다. `full`(피아노+반주)과
`piano`(원곡만)도 고를 수 있다. 세 가지 모두 **합쳐 둔 MIDI 에서 채널을 걸러** 만들기
때문에 타이밍이 완전히 같다 — 따로 만들면 어긋날 여지가 생긴다.

여기서 두 가지가 따라 나왔다.

### 반주가 곡 전체에 깔려야 한다

지시서 5장의 기본 연출 곡선 `build`(곡을 4등분해 off → simple → normal → rich)는
음원에 피아노가 있다고 보았을 때의 설계다. 반주만 내보내면서 그 곡선을 쓰면
**곡의 앞 1/4 이 완전한 무음**이 된다 — 실측으로 12마디 곡의 3마디가 `off` 였다.
아이는 그동안 맞출 것이 없다.

기본을 `flat`(곡 전체에 같은 두께)으로 바꾸고, 기본 두께도 `rich` 에서 `normal`
(pad + bass + color)로 낮췄다. 내내 `rich` 를 깔면 "용서하는 반주"가 아니라 시끄럽다.
`build` 는 발표회용으로 남겼다 — 무대에서는 아이 혼자 시작했다가 오케스트라가
밀려드는 그 효과가 실제로 살아나고, 그때는 지시서의 설명이 그대로 맞다.

8등분 구간별 평균 음량 실측 (12마디 곡, ♩=96):

```
mr    -18.8 -18.6 -18.7 -18.1 -18.7 -18.6 -18.4 -32.6   (마지막은 페이드아웃)
full  -18.8 -18.8 -17.9 -17.9 -19.0 -19.1 -18.8 -35.4
```

앞 구간이 무음이 아니다. 고치기 전에는 앞 두 구간이 사실상 무음이었다.

### 시작 신호가 필요하다

피아노가 없으니 반주가 어디서 시작하는지 알 수 없다. 카운트인을 음원에 구워 넣을 수
있게 하고, 카탈로그 곡은 1마디를 기본으로 뒀다. CLI 는 카운트인 없이 MR 을 만들면
그 사실을 알려 준다.

여기서 **잠복해 있던 버그**가 드러났다. 화성 확인 화면의 구간 재생이
`초 = 마디시작 × 60 / bpm` 으로만 계산하고 있어서, 카운트인을 구워 넣으면 그만큼
어긋난다. 서버가 `lead_seconds` 를 내보내고 화면이 더하도록 고쳤다. 브라우저 실측 —
카운트인 1마디(1.90초) + 3번 마디(3.81초) = **5.71초**, 기대치와 일치.

## 7. 남은 일 (1단계 범위 밖)

- **발표회 단골곡 10곡 검증** — 지시서 9장의 "완료 기준: 발표회 단골곡 10곡에서
  95% 이상"은 실제 부르크뮐러·체르니 MusicXML 이 있어야 돌릴 수 있다. 악보 확보는
  2단계 과제라 여기서는 못 했다. 회귀 하네스는 `fixtures/scores/` 에 악보를,
  `fixtures/truth/` 에 정답지를 넣으면 그대로 돌아간다
- **음질** — 기본 SoundFont(FluidR3_GM)로만 확인했다. 지시서 4장대로 현악 패드
  음색 하나만 바꾸면 체감의 70% 가 올라간다
- **연주 음원 경로** — 지시서 2.3 대로 악보와 짝지어 템포만 추출하는 용도. 미착수
